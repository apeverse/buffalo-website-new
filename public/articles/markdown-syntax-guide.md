# 软件的本质是什么？功能接口+语言编排

你有没有发现？几乎所有的“专业软件”，到最后都会藏着一门编程语言：
CAD 软件集成了 Lisp、Blender 内建 Python、数据库系统内置存储过程语言（如 PL/SQL、T-SQL）、
Web浏览器集成 JavaScript 引擎、Vim 和 Emacs 编辑器也分别集成了 VimScript 和 ELisp。
Excel 里还能跑游戏，想想为什么？

## 软件的本质是什么？

用一句话总结：

> 软件的本质，就是提供一组功能接口，让人类或 AI 可以通过点击拖拽去调用，或编写程序去灵活编排调用。

点击拖拽对应的是 GUI（图形用户接口），当软件功能足够复杂，靠鼠标或触控板是做不完事的，
这时你就需要像“说话”一样控制软件，而编程语言就是那种“说话方式”。GUI 是面子，语言才是里子。
操作系统作为硬件抽象层，也是提供一组 API，供各类语言编排调用。
而我们日常中所说的“编程语言”，基本上就是指可以独立运行在 OS 环境下的，典型例子：Rust/C/C++/Go/Java。
而那些嵌入到某个应用软件内部运行的，则被称为“脚本语言”，这类语言的代表：JavaScript/Lua/Shell。
只不过 Python 和 JavaScript 既可以独立运行在 OS 环境下运行，也可以嵌入在应用软件中运行。

## 你若喜欢发明创造，你就会撞到编程语言

想做一个新公链？ 不可能绕过“合约语言”。没有 Solidity 或 Move，智能合约如何写？链只是底座，语言才是灵魂。

想做新一代 Web 或浏览器？ 你就得考虑内嵌脚本语言。要么兼容 JS，要么发明一种 JS 替代，否则页面再漂亮，也是死的。

想造下一代操作系统？ 那你迟早要考虑系统编程语言，或许 OS 本身就是个语言解释器，不然整个设备就是个板砖。

当下我们已经进入 AI 时代，开发一个软件，不仅仅要考虑给人类去用，还要考虑如何给 AI 便捷高效地使用，同样需要思考编程语言的设计与实现。

## 我的经历：从功能到本质的回归

很多熟悉我的朋友可能觉得：

> “你怎么今天想做新型浏览器，明天又折腾公链，后天又鼓捣 GUI与Web3OS 软件，怎么老是跳来跳去？”

但我想说的是：我从未偏离方向，只是越来越靠近本质。

无论是做浏览器、公链、还是Web3OS，最终都发现：“没有一门适配的新编程语言，一切构想都是空谈。”

想做浏览器，结果卡在 JS 引擎，纠结要不要换掉这个老掉牙的东西；
想做链上世界，结果卡在智能合约语法设计与实现上，Solidity 和 EVM 的设计是失败的，最近技术社区在鼓吹 RISC-V，为啥呢？还不是因为折腾了几年 WebAssembly，没搞出啥名堂；
想做通用的 Web3OS 平台，又卡在图形脚本系统；
想利用 AI 技术做点事，做一套更适合 Web3 世界的人机协作系统，还是卡在“语言设计”层面。

软件的未来，不只是功能，而是：

> 能否用“语言”自由地组合功能？
> 能否让人类 or AI 灵活表达想法？
> 能否让用户“说出”他们想要的逻辑，而不是无数次的拖点拽？

## 我接下来应该去做什么？

所以“编程语言”不是程序员的玩具或工具，它是软件的终极接口、是功能的元调度器、是人与机器交互的真正桥梁。
操作系统的关键点：有效支持更多种、更现代的编程语言。
浏览器的关键点：要能执行更高效的脚本语言。
区块链的关键点：智能合约语言的表达力和安全性。
软件平台的关键点：是否内嵌一门好用的编程语言？别问“你开发的这款软件能干嘛”，要问的是：

> “我在 AI 的加持下，能用这款软件内嵌的语言拼出我想要的样子与结果吗？”

这才是软件的本质所在。幸好我这最近刚发现一门简单的语言：Koto，大致看了几天，发现它是真的适合编程语言设计与编译原理上手学习。

而对于常用的编程语言：Rust，C/C++，Java，Go，Python，JavaScript，语法细节太多，对应的编译器也已发展多年，
没有经过编译原理方面特别训练的人，是扒不动编译器代码的。而 Koto 才刚刚开始，天生就是个脚本语言，极简设计，适合编译器与 VM 研发入门。
我正在思考，如何基于 koto 作为模版设计一门全新的编程语言，为之前构思的那些产品打下坚实的基础，开辟一个新的、正确且有效的切入点、出发点。
而实现一门编程语言，只需要搞定这些： Lexer，Parser，Compiler，Linker，Loader，Interpreter，Executor，VM。
