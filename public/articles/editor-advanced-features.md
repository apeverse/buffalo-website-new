# 编程语言的选择：从图灵机到 Rust

若我们想透彻地理解：什么是计算，什么是编程，想透彻地搞明白哪种编程语言适合哪种计算任务，为什么要学习 Rust 等问题，
那么在对比和讨论具体的编程语言（C/C++/Java/JavaScript/Python/Go/Rust）之前，我们应该先要清晰地理解这些关键内容：

> 两个重要的计算机模型

- 图灵机
- 冯诺依曼机

> 两个重要的编程语言问题

- 内存管理机制
- 并发计算模型

理解了这些关键问题，并学会几门常用的编程语言，我们就构建起了开发者应该具备的认知框架。

## 图灵机是什么？

图灵机是科学家 艾伦·图灵 提出的一种极简抽象计算模型，它的目标是回答一个问题：

> “哪些问题是可以被计算出来的？”

它不是用来制造计算机的，而是用来定义“计算的本质”。 图灵机并不是直接“解释”计算的本质是什么，而是通过构建一个形式系统：

> 形式化地定义什么是“可计算”的。

### 可以这样理解

| 问题                     | 图灵机的贡献                        |
| ------------------------ | ----------------------------------- |
| 计算的本质是什么？       | ❌ **图灵机不直接回答这个哲学问题** |
| 什么东西是可以被计算的？ | ✅ **图灵机给出了形式化定义和边界** |

### 图灵机的构成

| 部件                                   | 描述                                                                                                                 |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **无限纸带（Tape）**                   | 理论上无限长的纸带，按小格划分，每格可存储一个符号，用于模拟内存。                                                   |
| **纸带符号集（Tape Alphabet, Γ）**     | 包含所有可以出现在纸带上的符号，包括**空白符号 B**。                                                                 |
| **输入符号集（Input Alphabet, Σ）**    | 是纸带符号集的子集，不包括空白符，初始输入来自于此。                                                                 |
| **读写头（Head）**                     | 负责在纸带上**读取当前格子的符号**，**写入新符号**，并按照程序指令**向左或向右移动**。                               |
| **状态集合（States, Q）**              | 包含所有可以出现的内部状态，包括：<br>**初始状态（q₀）**、**接受状态（q_accept）**、**拒绝状态（q_reject）**。       |
| **转移函数（Transition Function, δ）** | 规则表，根据**当前状态和读入的符号**，决定要：<br>① 写入什么新符号，② 进入什么新状态，③ 读写头向左、向右移动或不动。 |

> 符号读音：δ(delta) Γ(Gamma) Σ(Sigma)

```
用图灵机计算：f(x) = x + 1
在纸带上，用 [1] 表示数字 1，而 [1][1][1] 则表示数字 3

初始状态：q0
初始纸带：
[1][1][1][B][B][B]... // 输入为 111（即 x = 3）
 ↑
读写头

图灵机程序：
δ(q0, 1) = (q0, 1, →) // 读写头在 q0 状态下，若读到 1，则写入 1，并继续向右移动
δ(q0, B) = (q_accept, 1, -) // 读写头在 q0 状态下，若读到 空格，则写入 1，然后停止
// 以上两条语句规则，会让读写头一格一格跳过纸带上的所有 1，直到遇到空白 B

纸带最终结果：
[1][1][1][1][B][B]... // 输出为 1111，即 f(x) = 4
             ↑
           读写头
```

## 冯诺依曼机是什么？

科学家 冯·诺依曼 设计出一种真正可以制造出来的计算机结构，今天我们用到的几乎所有计算设备（包括你现在用的手机）都基于这个结构。
冯诺依曼机推动了“存储程序（stored-program）”的概念，将数据与程序一致对待，都放在内存中，程序指令逐条读取执行，这就催生了现代意义上的“编程”。
“存储程序”现在看起来再普通不过了，但首次成功践行这个设计方案还是相当了不起的。而图灵机没有存储程序的概念，
读写头相当于传输总线，转移函数相当于是程序（不是存放在纸带上），纸带的作用相当于打草稿，只是记录中间数据与最终结果。

### 冯诺依曼机的构成

| 组件          | 功能对应                                            |
| ------------- | --------------------------------------------------- |
| **运算器**    | 执行算术与逻辑运算（如加法、比较等）                |
| **控制器**    | 读取指令并按顺序执行（如 if、for 语句）             |
| **内存**      | 存储指令与数据（RAM）                               |
| **输入/输出** | 与外界通信（I/O设备：键盘、鼠标、屏幕、硬盘、网络） |
| **总线系统**  | 连接各个部件，传递数据与控制信号                    |

运算器 + 控制器，构成CPU的核心部分，但实际制造的CPU芯片还包括：寄存器、Cache等其他优化设计。

## 图灵机与冯诺依曼机部件构成对照

| 图灵机（理论模型） | 冯诺依曼机（工程结构）             | 解释               |
| ------------------ | ---------------------------------- | ------------------ |
| **纸带（Tape）**   | **内存**                           | 存储数据与中间结果 |
| **读写头（Head）** | **程序计数器 + 寄存器**            | 读/写位置控制      |
| **状态（State）**  | **控制器的当前指令状态**           | 决定下一步动作     |
| **转移函数 δ**     | **程序代码（表达逻辑）**           | 控制执行流程       |
| **输入/输出符号**  | **I/O 设备：键盘、显示器、硬盘等** | 人与计算机之间交互 |

## 编程语言的设计与选择

现在我们继续讨论编程语言（Programming Language，PL）的话题，对于常见的 PL（C/C++/Java/JavaScript/Python/Go/Rust）来说，
他们的计算能力是等价的，以上 7 种 PL 也被称为是“图灵完备”的，原因是：若世界上有某些问题，用图灵机写不出算法程序，解决不了，
那么用他们同样解决不了，若用图灵机能够解决，用他们同样也能解决。
图灵机模型虽然简单，但算法描述能力和这些编程语言是完全等价的（非正式地讲，因无限内存的优势，图灵机或许还更强，只是用起来不方便）。
既然他们的计算能力或潜力是等价的，为什么计算机行业要设计出那么多种 PL？这个就要讲到理论和实践的区别、图灵机与冯诺依曼机的区别。
实际可用的 PL，运行环境是冯诺依曼机，控制流（if else while for loop...）对应控制单元，
运算符与表达式对应算术逻辑单元（ALU），所以表面上看这些 PL 都差不多。而将他们真正区分开的，是两个至关重要的设计点：1）内存管理； 2）并发模型。

### 内存管理

由于实际运行环境中没有无限内存（纸带格子）可用，所以需要分配和回收内存空间，有以下三种内存管理思路：

- 1）运行时自动管理内存（Java/JavaScript/Python/Go）
- 2）编译器智能处理内存（Rust）
- 3）程序员手动释放内存（C/C++）

这三种处理方式，直接关系到学习负担和上手使用的难度：

- 第 1 类，最容易学习和使用，没有安全心理负担；
- 第 2 类，需要一个学习爬坡期，掌握之后非常好用，没有安全心理负担；
- 第 3 类，最难学习和使用，容易出安全世故，安全心理负担较重。

| 模型/语言         | 内存是否无限 | 内存管理方式          |
| ----------------- | ------------ | --------------------- |
| 图灵机            | 无限         | 不需要管理            |
| 冯诺依曼机        | 有限         | 必须进行管理          |
| C/C++             | 有限         | 手动管理              |
| Java/JS/Python/Go | 有限         | GC自动管理            |
| Rust              | 有限         | 生命周期 + 所有权系统 |

Python、Java、Go、JavaScript 都内置了 GC（垃圾回收机制），自动回收不再使用的内存。
常见的回收算法是引用计数：谁还在用对象，计数就加一；没人用了，系统自动清理。

```
// 代码片段 Python
a = SomeObject()    # 创建对象，引用计数 = 1
b = a       # 引用计数 = 2, a 和 b 都指向同一对象)
del a       # 引用计数 = 1, 只是删除了变量名 a, 对象仍然存在，因为 b 还在引用它
del b       # 引用计数 = 0, 这时才可能被 GC 回收

// 代码片段 Java
SomeObject a = new SomeObject();    // 创建对象
SomeObject b = a;   // b 也引用同一对象
a = null;           // a 不再引用对象, 但仍然被 b 引用，不会被回收
b = null;           // 现在对象可能被 GC 回收
```

> GC 虽然方便，但也可能带来性能波动，特别是在回收时可能“卡顿”。

C 和 C++ 要求程序员手动分配和释放内存。 若忘记 delete，内存就泄露，若多次释放，程序就崩溃；

```
int* p = new int(10);
delete p;
// 此处可再写多次 delete p，语言本身并未强制报错，要看编译器自身是否贴心告警
```

Rust 采取的是所有权与生命周期机制，不依赖GC，也不用手动释放,变量在离开作用域时自动释放，同时编译器在编译期检查是否有悬空引用或重复释放。

这就是 Rust 的魅力：安全、无GC、零成本抽象！

```
fn foobar() {
    let s = String::from("hello");
    println!("{}", s);
} // 到这里会自动释放掉 s 对应的内存空间
```

虽然现代 C++ 也引入了 RAII（Resource Acquisition Is Initialization）机制，其核心理念是：

- 当一个对象被创建（初始化）时，就自动获取资源（如内存、文件句柄、互斥锁等）
- 当这个对象被销毁时，自动释放资源

C++ 和 Rust 相比，仍有重要区别：

- 这些机制不是强制使用的（不像 Rust 编译器强制你使用所有权/借用）
- 你仍然可以用裸指针、手动 new/delete 写出危险代码
- 旧代码库和一些底层库开发仍然广泛使用传统方式

用一句话总结就是：最新 C++ 提供了很多现代化自动内存管理工具，但它的“自动”是依赖开发者自觉选择使用，而不是由编译器强制或语言内建机制保障。

### 并发模型

图灵机和冯诺依曼机的作用是表达数学算法与物理机器相关的核心概念，并没有强调并发计算与并发 I/O 处理等能力。
且现代 CPU 早已是多核计算，计算设备中大多配置多个 CPU 与协处理器 GPU、TPU 等，
在现代 APP 应用中，程序不仅要能跑得对、跑得快， 还要能“同时做很多事情”，
比如视频场景：一边下载，一边播放，一边聊天。这就引出了另一个维度的挑战：并发编程模型。

> 并发的本质是多个任务共享资源并交替执行，既可以用多线程或多进程，也可以用异步协程和事件循环的单线程模型来实现。

Rust 在并发处理方面的安全优势在于：它在编译期强制检查数据访问规则，
从根源上防止数据竞争（Data Race）和空悬指针等常见错误，而不是运行时才发现问题。

我们用个经典的例子说明：

```
// 代码片段 (C++)
int counter = 0;

void thread_func() {
    counter += 1;  // 没有加锁，多个线程可能同时执行这行语句，运行结果不可预测
}
```

在多线程场景中，如果多个线程同时访问和修改 counter，就可能造成数据竞争（Data Race），导致结果不可预测。
但在 Rust 程序中，这种情况天生就可以避免，因为编译器会报错，强制开发者用`Arc<Mutex<T>>`等方式解决报错。
具体的代码示例这里就不展开了，因为很容易搜索到，各种语言的典型做法与效果，可用下表总结：

| 语言       | 数据竞争预防方式           | 编译时检查？        | 内存安全？    | 常见问题示例                         |
| ---------- | -------------------------- | ------------------- | ------------- | ------------------------------------ |
| C/C++      | 手动加锁/volatile          | ❌ 否               | ❌ 否         | 空悬指针、野指针、竞态条件           |
| Java       | synchronized/volatile      | ❌ 否               | ✅ 是         | 需要开发者手动加锁                   |
| JavaScript | 单线程事件循环+Web Workers | ✅ 部分（基于语义） | ✅ 是（沙箱） | 异步陷阱、回调地狱                   |
| Python     | GIL 限制了并发能力         | ✅ 一定程度         | ✅ 是         | 真正的多线程受限                     |
| Go         | goroutine+channel          | ✅ 部分             | ✅ 是         | 数据竞争靠工具发现（`go run -race`） |
| **Rust**   | 编译器检查所有权+借用      | ✅ 强制             | ✅ 强         | 无数据竞争，编译期报错               |

## 为什么学编程，要首选 Rust？

内存管理和并发处理，是编程的关键，经过以上的论述，最终可得以下对照结果：

| 特性                          | Rust          | 其他语言                                 |
| ----------------------------- | ------------- | ---------------------------------------- |
| 编译时防止数据竞争            | ✅ 是         | ❌ 否（Go 靠 race 工具协助检测而非解决） |
| 所有权/借用系统防止野指针     | ✅ 是         | ❌ 否（C/C++ 普遍存在）                  |
| 无需 GC 也能避免内存泄漏      | ✅ 是         | ❌ 否（C++ 容易产生内存泄漏）            |
| 并发模型的强制封装（Mutex等） | ✅ 编译器强制 | ❌ 靠开发者自身习惯                      |
| 零成本抽象（无运行时开销）    | ✅ 是         | ❌ Java/JS/Go/Python 有 GC 和调度开销    |

若抛开具体的编程任务不谈（每个语言都有自己特别擅长的领域），笼统地讲，想要系统性地学习编程，最好选择 Rust，
在 AI（LLM，大语言模型）普及应用之前， 学习 Rust 会有不少语法层面的记忆负担，但现在已有 DeepSeek、ChatGPT、Claude 等平台可以随时提问，
还有 Cursor 这类与 LLM 密切集成的 IDE（集成开发环境），学习难度与成本至少降低一半。 尽管如此，
你仍需大约 3星期 ～ 3个月 的时间（视编程基础而定）去熟悉 Rust 的各个细节特征，而一旦度过这段学习爬坡期，即可充分利用 AI 协助开发产品了。
